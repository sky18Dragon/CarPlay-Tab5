# iPhone 12 Pro Max / iOS 16.1.1 未进入 CarPlay：配对状态保存失败

## 结论

本次直接阻点已确认：用户在手机上确认信任后，Tab5 更新本地配对记录失败，返回 `ESP_ERR_NVS_NOT_ENOUGH_SPACE`，随后状态机进入 Failed / CP_ERR_STORAGE。不能据此判定 iOS 16.1.1 不兼容；TLS、iAP2 和媒体尚未走到，兼容性也不能提前认定通过。

当前固件具备按手机身份保存多份记录的逻辑，但现有 24 KiB NVS 与整块更新方式限制了实际换机能力。此前“可直接换其他 iPhone”的答复遗漏了这一限制。

## 实机证据

串口证据：`artifacts/device-2026-11-13/iphone12-pairing/followup-runtime.log`。

- 第 14 行：实际设备 NVS 分区为 `0x9000 / 0x6000`，即 24 KiB。
- 第 442 行附近：NCM 接口就绪，当前手机 IN=88 / OUT=06，表明描述符自动发现识别了与上一部手机不同的接收端点。
- 第 452 行：`LOCKDOWN_QUERY_TYPE_OK`，USBMUX/Lockdown 基础查询成功。
- 第 457–458 行：NVS entries used=486、free=270、total=756；配对 blob=2，合计 13536 字节，每份 6768 字节。
- 第 467 行：`PAIR_RECORD_REUSED phone key matched; trusted=pending`。当前手机的身份记录已经存在，仍处于本地未确认信任状态。
- 第 469 行：等待手机信任；用户随后明确确认已点击信任。
- 第 477 行：`Pair persistence failed: ESP_ERR_NVS_NOT_ENOUGH_SPACE; existing NVS is not erased`。
- 第 480 行：`SESSION: stage=Failed error=5`，对应图片上的 “Pairing storage unavailable. Existing records preserved.”。
- 失败后 USB STATUS、NCM STATUS 仍持续输出，未发生 USB 任务卡死。

## 为什么只改一个状态也写不进去

`main/lockdown_client.cpp:432` 在收到成功的 Pair 回复后把 `trusted` 从 0 改成 1，再调用 save。save 在第 109 行使用 `nvs_set_blob` 重写整个 6768 字节 PairRecord，其中包含证书、身份和私钥，即使本次实际只改变一个信任状态字节。

ESP-IDF NVS 不会直接覆盖原 blob，而是先写新版本，再回收旧版本，且需要保留页供垃圾回收。因此日志中的 free=270 不能简单乘以 32 当作可用于此次更新的连续空间。此处明确失败的是存储分配，不是手机拒绝信任，也不是普通运行堆不足。

依据：本机 ESP-IDF v5.5.3 的 `nvs_storage.cpp` 先调用 writeMultiPageBlob 写新版本；`nvs_pagemanager.cpp` 保留用于回收的空闲页。官方说明同样要求更新期间容纳旧、新两份数据：[ESP-IDF 文件系统与 NVS 注意事项](https://github.com/espressif/esp-idf/blob/v5.5.3/docs/en/api-guides/file-system-considerations.rst)。

当前故障路径没有擦除既有配对，因此重新插拔会再次读取 trusted=pending，并可能重复失败。重复信任或重启不改变这个空间问题。

## 建议修复

优先将易变的信任状态与身份大 blob 分离：保留现有两份身份记录，将 trusted 存成按手机索引的独立小整数键；加载时优先使用独立状态，旧记录不存在该键时回退到旧 blob 内的值。确认信任以及 InvalidHostID/InvalidPairRecord 失效时都必须更新同一状态路径，不能只修确认信任的一处。

实现需校验完整手机公钥摘要，避免截断键碰撞或陈旧状态关联到错误身份；身份重新生成时也要处理状态的一致性。写入失败仍应停止并保留已有记录，不通过“先删旧 blob 再写新 blob”腾空间。

这能避免本次 1 字节状态变更引发 6.8 KiB 重写，但不代表 24 KiB NVS 能无限容纳新手机。长期多机支持还需紧凑存储或专用配对空间，并设计保留已有身份的迁移与失败回退。不能直接扩大当前 NVS 尺寸，因为后面紧邻 phy_init 与 factory。

本轮仅完成诊断，未修改业务代码、未烧录、未主动删除或清空任何配对记录。手机确认信任时原固件自行尝试保存状态，该保存失败已如上记录。


## 用户授权清理后的恢复结果

用户明确允许清除旧记录重新配对后，使用已有 `TAB5_PAIR_RESET_MAINTENANCE` 维护模式，仅对 `tab5_pair` 句柄执行 erase/commit；返回 `PAIR_RESET: namespace=tab5_pair result=ESP_OK`，并验证此命名空间已无条目。未清空整个 NVS，未修改其他命名空间。

随后烧回原正式镜像 `cb916322`，Hash verified。启动统计 NVS used=54/free=702，pair blobs=0。手机重新确认信任后：

- 31.879 s：`PAIR_OK identity saved for this phone`。
- 32.824 s：Lockdown TLS_READY；33.723 s：CarKit TLS_READY。
- 34.285 s：`IAP2_AUTHENTICATED phone accepted challenge response`。
- 47.428 s：`SESSION: stage=Streaming error=0`，随后视频解码计数持续增长。
- 用户明确确认已显示 CarPlay 画面。
- 首段音乐收到 3361 包，bad=0；期间音频丢包、乱序、欠载、提交拒收均为 0。

这证明本次配对存储故障已通过清除旧记录恢复，且这台 iPhone 12 Pro Max / iOS 16.1.1 的基础 CarPlay 视频和音频链路已跑通。没有实现长期多机存储方案，换回旧手机时需要重新配对，继续积累记录仍可能遇到容量限制。

维护开关已经关闭（`TAB5_PAIR_RESET_MAINTENANCE=OFF`），软件认证保持 ON，本地重新构建的 `build/carplay_tab5.bin` SHA-256 与 `cb916322` 原正式镜像一致。设备没有留在会开机清记录的维护版本。证据：`reset-runtime.log`、`repaired-flash.log`、`repaired-runtime.log`，均在上述本地证据目录。
