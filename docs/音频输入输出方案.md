# Tab5 CarPlay 音频输入输出：现状分析与实现方案

2026-11-08。现象：在 Tab5 上点 QQ 音乐播放，声音从手机出；Siri 等语音输入也用手机麦克风。

## 0. 进展

- 2026-11-08 阶段 0–1 完成：声明麦克风输入后，手机立刻建立了 media 流，QQ 音乐从 Tab5 出声；Siri 建立了 24 kHz 的 speechRecognition 流，静音上传正常。根因已证实。详见 `docs/执行记录.md`。

## 1. 结论

最可能的原因：Tab5 向 iPhone 声明的音频能力只有输出，没有麦克风输入。iPhone 因此不把 Tab5 当作完整的 CarPlay 音频设备，所有声音都留在手机上，输出列表里也不出现 CarPlay。

证据：
- **实机日志**：`artifacts/device-*` 里共 142 次会话，手机只建立过视频流（`stream_ready type=110`），从没对 Tab5 发起过音频流 SETUP（type 100/101），所以 `AUDIO` 日志一条都没有。接收和播放代码一直在，但从没被调用过。
- **DiPlay issue #288**：用户关掉 DiPlay 的麦克风权限后，音乐和导航全部改从手机外放，输出列表里也没有 CarPlay。维护者判断：不提供音频输入，iPhone 就不把接收端当作完整音频设备；办法是“仍声明输入，并上传静音”。这和我们的现象一致。
- **声明对照**：

| 项目 | Tab5 现在 | DiPlay（能出声） | Carplay-S3 |
|---|---|---|---|
| `features` | `0x615653aee2` | 相同 | 相同 |
| 音频流种类 | 3 种：type 100 的 default、media、alert | 9 种 | 8 种 |
| `audioInputFormats`（麦克风） | **无** | compatibility、default、telephony、speechRecognition 都有 | 无（也从没收到过音频） |
| telephony、speechRecognition | 无 | 有 | 有 |
| type 101 辅助音频（导航提示） | 无 | 有 | 有 |
| type 102/103（AAC 音乐） | 无 | 102 AAC-LC，103 可选 | 无 |
| `extendedFeatures` | enhancedRequestCarUI | 另有 vocoderInfo | — |

Carplay-S3 同样没有声明输入，它的文档也记录了“未取得实际音乐 PCM 接收”，这从侧面印证了上面的判断。

## 2. 协议要点（以 DiPlay 为准）

**流类型**：100 主音频，按 `audioType` 区分 default、media、alert、telephony、speechRecognition、compatibility；101 辅助音频，用于导航提示等；102 主高质量音频（AAC）；103 主缓冲音频（AAC，需要 `mainBuffered` 特性）。

**下行（手机→Tab5）**：
- RTP 包加 ChaCha20-Poly1305 加密。RTP 头的 timestamp 和 SSRC 作为 AAD，包尾是 16 字节 tag 加 8 字节 nonce。
- 密钥用 HKDF-SHA512 派生：输入为 Pair-Verify 共享密钥，salt 为 `DataStream-Salt<streamConnectionID>`，info 为 `DataStream-Output-Encryption-Key`。
- 负载是大端 16 位 PCM。
- 现有 `airplay_audio.c` 已经实现了这一部分。

**上行（Tab5→手机，麦克风）**：
- 手机在音频流 SETUP 里给出它的接收端口 `dataPort`。
- 密钥派生方式同上，只是 info 换成 `DataStream-Input-Encryption-Key`。
- RTP 头里 payload type 等于流类型（100）。每发一包，序号加 1，timestamp 加上本包的采样数，nonce 计数器（小端）加 1。
- 负载是大端 PCM。48 kHz 单声道每包 10 ms，保证不超过 1452 字节的 MTU；16 kHz 和 24 kHz 可以每包 20 ms，或按手机给的 `framesPerPacket`。

**何时开麦**：
- telephony 和 speechRecognition 一定要开麦。
- default 和 compatibility 只在手机要求输入时开麦：`input` 为真，或给了 `dataPort`。
- 收到第一个下行包就开始采集。Siri 这类可能没有下行声音，SETUP 后 500 ms 也要开始采集。
- 通话时同一条流的上下行用同一个采样率，手机为这条流只选一个 `audioFormat`。

**格式位**：
- PCM 单声道：8k `0x4`、16k `0x10`、24k `0x40`、32k `0x100`、44.1k `0x400`、48k `0x4000`；对应的立体声是单声道位乘 2。
- Opus：`0x10000000`（16k）、`0x20000000`（24k）、`0x40000000`（48k）。
- AAC-LC：`0x400000`（44.1k）、`0x800000`（48k）。

**其他命令**：`duckAudio` 和 `unduckAudio` 标记导航提示的开始和结束，需要压低音乐音量。`requestSiri` 用来唤起 Siri，siriAction 2 和 3 分别是按下和松开。

## 3. Tab5 硬件约束

- ES8388（喇叭和耳机）和 ES7210（双麦 ADC）共用**一路 I2S 全双工**，收发是同一个采样率。BSP 默认 48 kHz、16 位、单声道。
- 所以 I2S 固定在 48 kHz，其他采样率在软件里转换：16k 和 24k 按整数倍上采样或下采样；媒体流只声明 48k，避免 44.1k 的分数倍重采样。
- CPU：视频解码占满两个核。按估算，48k 立体声 PCM 加 ChaCha 解密约占 1–2% 的单核，麦克风上行更少。回声消除（AEC）开销大得多，只在通话时考虑，而且要先实测。
- 喇叭、麦克风硬件还没有在实机上验证过（`CONFIG_TAB5_AUDIO_TEST` 自检没有日志记录）。

## 4. 分阶段方案

每一步都单独测量，无效就撤回。烧录只写 factory 分区，保留 NVS。

### 阶段 0：先加日志（约半天）
- 记录手机发来的每个 `/command` 的 type 和参数键名。现在只回 200，类型没有记下来。
- 记录 SETUP 里每条流的 type、audioType、audioFormat、input、dataPort、framesPerPacket。
- 用来确认后续每一步的效果。

### 阶段 1：声明输入，并上传静音（1–2 天，最关键）
- `info_*.plist` 改为 DiPlay 的声明集：
  - type 100：compatibility、default、alert、media、telephony、speechRecognition；
  - type 101：compatibility、default；
  - 加上 `audioInputFormats`（PCM 单声道 16k、24k、48k）、`audioLatencies` 和 `vocoderInfo`。
  - 先不声明 102/103，媒体流强制走 PCM。
- 由 `scripts/configure_tab5_info.py` 统一生成，保持 HID 描述符校验。
- `airplay_audio_start`：
  - 接受 8–48 kHz 的 PCM，以及 type 101；
  - 派生 Input 密钥；
  - 手机要求输入时，向它的 `dataPort` 上传**带标识的静音包**（日志写明 `uplink=silence`）。
- 验收：
  - iPhone 控制中心的输出列表出现 CarPlay；
  - 用 QQ 音乐播放时，日志出现 `AUDIO ready type=100 usage=media` 和 `PCM_FIRST`；
  - 视频帧率和拒收数不变差。
- 如果加了输入声明，手机仍然不建音频流，就把 `/command` 和 SETUP 日志与 DiPlay 的抓包逐项对比，再看 `modes` 和 iAP2 识别字段。

### 阶段 2：喇叭出声（1–2 天）
- 播放任务在两个解码任务之上，I2S 固定 48 kHz。
- 主音频和辅助音频软件混音，16k 和 24k 上采样到 48k。
- 抖动缓冲 100–150 ms，用来吸收解码占用 CPU 带来的抖动。用丢样或补样的方式跟随手机时钟。
- 处理 `duckAudio` 和 `unduckAudio`，导航提示时把音乐压到约 30%。
- 验收：音乐连续播放 10 分钟，欠载次数可统计且接近 0；导航提示能压低音乐；视频指标不变差。

### 阶段 3：麦克风上行（1–2 天）
- ES7210 以 48 kHz 采集，下采样到协商的采样率，转成大端，加密后打包上传，替换阶段 1 的静音。
- Siri：长按 CarPlay 主屏图标，或加一个本地按键发 `requestSiri`。
- 验收：Siri 能听懂、能回答；上行包计数正常，没有超过 MTU 的包。

### 阶段 4：通话（视资源而定）
- 回声消除可以用 esp-sr 的 AFE（支持 ESP32-P4）。参考信号需要确认 ES7210 是否有回采通道，M5 官方 Demo 用的是多通道 TDM。
- 先实测 CPU 占用。必要时通话期间降低视频帧率。

## 5. 风险

- 输入声明是否就是根因，现在只能根据 DiPlay 的案例推断。阶段 1 的成败就是验证。
- 不同 iOS 版本可能改用 Opus 或 AAC。这里只声明 PCM，如果手机坚持用压缩格式，需要再加解码器。
- 音频任务优先级高于视频解码后，视频帧率可能下降，需要和阶段 1、2 的数据对比。
- 声明有麦克风但实际不能用，会导致 Siri 和通话没有声音。阶段 1 的静音版本只能用于测试，不能发布。
